# Netcode

dot-net's own rules are in [dot-net's CLAUDE.md](../../dot-net/CLAUDE.md) and its reasoning in [docs/](../../dot-net/docs/README.md); this is what is specific to the arena's bridge.

## The bridge

`ArenaNetBridge` is the only file that names both `ArenaGame` and `DotNetManager`, and it is a file rather than a few lines because the ordering is the hard part. dot-net simulates per entity; this game's tick order is a whole-game property ([architecture](architecture.md#order-inside-a-tick)). Those meet in `ensure_game_ticked`: the first `_net_simulate` on a given tick drives the entire game and the rest find it done.

- **`Authority.SHARED`, not `SERVER`.** The server stays authoritative and corrects; the owning client predicts. `DotNetIdentity.is_predicted()` is false for any other authority, so `SERVER` would mean a player seeing their own movement a full round trip late.
- **The acknowledgement rides the input packet.** dot-net owns no client-to-server channel, so `encode_ack()` produces four fixed-width bytes in front of the bit-packed command: in front, because a bit-packed command is not fixed width and a reader that had to skip it would have to decode it first.
- **The server tick calls `ensure_game_ticked` again afterwards.** A server with no players registered runs no behaviours at all, and the match clock still has to advance.
- **`receive_snapshot` must not reconcile.** `DotNetManager.receive_snapshot` already routes a predicted entity's state to `DotNetPredictor.reconcile` and acknowledges the inputs it covers. A second pass on top replays the same inputs against already rewound values; the client still converges, and the only visible cost is `correction_rate()` near one half, which `DotNetPredictor` documents as "the two simulations disagree".

`ArenaPlayerNet` resolves `DotFpsNetSync` and `DotCombatNetSync`'s specs against `DotNetVar.Type`, which is why neither addon has to know dot-net exists. Ammunition is `to_owner_only()`: not a bandwidth saving, but because exact ammunition is information an opponent should not have, and data never sent cannot be read out of a modified client.

## One number, written once

`ArenaGame.NET_WORLD_EXTENT` and `NET_SNAPSHOT_RATE` are constants on the game because the module and the client both build a `DotNetConfig`, and a quantised position decoded against a different range is a different position, not a less precise one. Written separately (128 in one file, 256 in another) it looked like a client that connects, seals a byte-identical schema, adopts its player alive, and draws sky in every direction with no error anywhere. `headless_net._test_config_agreement` asserts the two ends agree on the extent, the tick rate and the schema hash.

The extent is 512 because the combat surf maps reach 312 m from the origin; at 128 every position on the far half of one was clamped to the quantiser's edge.

## A server declares the rate it ticks at

A server's tick rate is the host's `sv_tickrate` (`ArenaServer.host_tick_rate()`, set before `setup`), never `ArenaGame.tick_rate`'s 64: `ArenaModule` runs one tick per physics frame, and dot-server sets the physics rate (60 by default). Declaring 64 on a 60 Hz server (until 2026-10-21) ran every client's clock 4 ticks a second ahead of the snapshots: `tools/client_bench.gd --tick 64 --play` measured 2051 of 2052 reconciles with no prediction to compare (every snapshot overwrote the player) and 87 clock catch-ups in 25 s; at `--tick 60`, 723 of 749 matched and 14 catch-ups. The snapshot rate is `ArenaGame.snapshot_rate_for(tick_rate)` on both ends (30 at 60 Hz), because dot-net divides with integers and 32 at 60 Hz sent every tick. `dedicated` checks both.

## The client predicts with the server's collision

The client uses `Mode.HEADLESS` collision, on a client with a screen. `HEADLESS` is `ArenaMap`'s analytic geometry, the same list of boxes the meshes come from, and it gives the same answer on a client replaying a tick as on the server that ran it. **A predicting client must use the same collision backend as the server it is predicting against.** Godot physics on the client is a second solver with its own contact epsilons, and reconciliation would correct a client that had done nothing wrong. (`Mode.PHYSICS` also wants a collision shape on the player node, and `ArenaPlayer` is a plain `Node3D`: the player fell through a floor that was drawn perfectly.)

An imported map gives every player a `DotFpsPhysicsBody` bound to the map's brushes, which both ends put in the tree alike, so the rule holds ([imported maps](imported-maps.md#the-solid-is-the-games-on-every-machine)).

## The owner rewinds from the exact state

The same collision is not enough: a replay only lands where the server did if it starts where the server was. The movement properties everybody gets are quantised (`net_position` to 1 cm, `net_velocity` to about 5 cm/s), and the motor is not smooth at that scale beside a wall, on a stair tread or at the floor's skin: half a centimetre is touching a wall or not, standing on a tread or walking into its face, grounded or falling for a tick. So the owner also gets `net_exact` (`ArenaPlayerNet`, owner-only): position, velocity and crouch as float32, which `_net_state_applied` puts over what `DotFpsNetSync.push` restored. Observers still interpolate the quantised copy. It is a `PackedFloat32Array` under a custom codec because dot-net compares a custom property exactly after a round trip, and it is declared in the pack rather than in dot-player-controller so both ends declare the same properties whatever addon a client's shell carries.

Found 2026-10-18 with a headless probe that rewound one player round dm_atrium to its own earlier snapshots and replayed: from the quantised state 594 of 994 replays left the snapshot's match within 8 ticks, from the exact state 1. Finer quantisation only shrinks it (20 of 994 at a quarter of a millimetre and 18-bit velocity), because the slack a match is judged with shrinks with the quantum. dm_box hid it: running flat in the open touches nothing. In `tools/client_bench.gd` (dm_atrium, `--play --delay 40`, 25 s, no bots) it took the correction rate from 17.8% to 7.0% and the movement mismatches from 7 to 5; most of what remains is `net_challenge_value` and `net_flags`, at about one replay a second. Exact float32 equality assumes a browser client steps the same float32 arithmetic as the server; a last-bit difference costs one replay, not a wrong position.

## A joining client is told the map at READY

A client builds its world on dm_box and learns the server's map from dot-map's sync host. The module used to register a joiner with `add_peer`, which only enrolls it for the next change, so a client that joined a server on any other map (any server after its first rotation, or one started with `--map`) stayed on dm_box for the whole map: drawn on the wrong level and predicting against the wrong walls. `client_bench` on dm_atrium measured 2.4 replayed ticks and 0.5-0.6 ms of reconciliation a frame, with a correction on 83-95% of snapshots and errors up to 3.5 m; that is the multiplayer lag. Now `ArenaNetBridge.peer_ready_fn` admits the peer when it says READY (`ArenaMapDirector.admit_peer`, which announces the current map; nothing reaches a client before READY), and `ArenaClient._on_map_changed` rebinds every player's movement to the adopted map, as `ArenaGame.change_map` does on the server. After: 0.07 replayed ticks and under 0.1 ms a frame.

A connected client's loading cover stays up over that dm_box placeholder (`ArenaClient` keeps the `map` hold from boot) until the first `_on_map_changed`, or until the map is refused or the change abandoned. Released at boot, the cover lifted on dm_box a round trip (or a download) before the server's map arrived and came back for it: the player saw and walked the wrong level, and the cover report told the server the seat was loaded, so it was harmable behind the second cover. `headless_feel` checks the order (the cover first lifts after the server's map is in); `dedicated` checks that READY, not the seat, admits a peer to the map sync and announces the map.

## No rate cap by default

`sv_maxrate` (bytes a second per client, `DotNetConfig.per_client_budget`, live) is 0, no cap. A client costs about 6 kB/s in play and 16 kB/s while joining; a cap that bites does not shrink a snapshot, it holds it back, which a player sees as a ping spike. Set it only to protect a thin uplink.

## Players are solid to each other

`mp_solidplayers` (dot-player-controller's `DotPlayerBodyRules`, `ArenaGame.body_rules`, 1 by default) is bound REPLICATED by the module and followed by the client, because the client predicts its own player against the others. The family's hull is a capsule in the physics space, which arena's analytic movement never asks, so arena does it in the movement body: every player's body is `arena_solid_body.gd` around the map's (`ArenaPlayer._movement_body`), and its sweeps also stop at the other living players' standing hulls (`ArenaGame.solid_hulls_for`: boxes, two radii across, from where each stands now). Only the sweep sees them; `overlaps` and `rest_contact` answer for the map, so two players placed inside each other walk apart and are solid once clear (the family's pass-out rule). Players tick in one order on every machine, so a mover meets the others where they are at that point in the tick. A client replays against the others where it last heard they are, which agrees with itself and can differ from the server by centimetres while two lean on each other; `headless_net` measured 5 mm. The wrapper copies the controller's mask and exclusions onto the map's body, so an imported map's physics body asks what it asked unwrapped. Players and bots alike; there is no hull for monsters or props here.

## Drawing between ticks

`ArenaPlayer.present` uses `DotFpsController.render_state`, and `ArenaNetBridge._adopt_tick_rate` moves `Engine.physics_ticks_per_second` as well as the game's, the config's and the clock's. Either half alone measures as no better than nothing: the fraction a renderer interpolates at is a fraction through a physics frame, which is a fraction through a tick only while the two rates agree.

**The view and the eye are drawn once a frame, not once a tick** (2026-10-10). `ArenaPlayer.present` drew the state's yaw and pitch, which only a tick moves, and this game ticks 64 times a second: on a 144 Hz display more than half the frames run no tick (80 of every 144), and on each the view stood still while the mouse moved and turned double on the next frame. game-g2gfast measured it over a real socket at 128 ticks (96 of 864 frames still at 144 Hz, its `headless_feel`); here it is arithmetic, not measured over a socket. `ArenaClient._fold_look` calls `DotFpsSampler.look_now()` (dot-player-controller) every frame and present draws `ArenaPlayer.view_now`, the own-body yaw included; the commands do not change, since the sampler's angles are cumulative. And `ArenaClient._fold_correction` hands `DotNetPredictor.visual_offset` to `ArenaPlayer.drawn_offset`, which present adds to the eye: dot-net always computed what is left of a correction to ease, and nothing read it, so a correction moved the eye in one frame (30.4 cm in one frame for a 30 cm correction in g2gfast; eased, 4-5 cm at most). Both by name or by plain field, so a shell older than `look_now` draws as before. `headless_presentation`'s *A frame with no tick in it still turns the view* draws a frame with mouse motion and no tick (armed by drawing the state's angles and dropping the offset: two of three fail); `_fold_correction`'s plumbing needs a predicting client and is reached by g2gfast's twin, not by a suite here.

**Connected, the eye is drawn at the clock's render alpha, not the engine's fraction** (2026-10-11). The client's ticks are `DotNetClock`'s, which stretches or shrinks them while it settles on the server (drift), so now and then a physics frame runs no tick and a later one two; drawn at the engine's fraction the frame after one with none went back over the step it had drawn and the frame after one with two moved double: `headless_feel` measured 4 to 8 frames in 5 s 10 to 16 cm off at 60 Hz and through 5% loss. `ArenaClient._fold_alpha` hands `DotNetClock.render_alpha()` (dot-net) to `ArenaPlayer.drawn_alpha`, which carries the slip and takes it back at a tenth of a tick per tick, so it runs from -1 to 2 for a moment: `ArenaPlayer._render_state` goes on along the last tick's step past 1, and below 0 draws between the two ticks before from `_position_two_back` (the controller keeps only two states). By name, NAN on a shell older than `render_alpha` and offline, where every physics frame is one tick. Remote players get the same through dot-net's `interpolate_frame`, plus the receive timeline's re-anchoring followed gently (`receive_slip`) and a resumed snapshot stream eased back rather than snapped: dot-net's [timelines](../../dot-net/docs/timelines.md).

**A link that slows is followed by the server's word, not the round trip** (2026-10-11). The client's input lead followed ENet's smoothed round trip, so when it grew (40 to 70 ms each way in `headless_feel`) the commands reached the server after their tick for seconds, the server repeated the last one and the prediction was corrected 38 to 76 times in 5 s, the eye going backwards on 56 to 111 frames. dot-net's server now says in each snapshot how early this client's commands arrive and its clock steers to keep them two ticks early ([dot-net timelines](../../dot-net/docs/timelines.md#the-input-lead-the-server-reports)): 0 late, 0 to 2 corrections, the eye judged and never backwards. Nothing here changed for it: the server measures arrival in the `DotNetInput.Buffer.push` that `ArenaNetBridge.receive_input` already calls, and the report rides in the snapshot, not in the input packet's `ACK_BYTES` prefix.

## Events and requests

`ArenaEvents.Kind` and the request kinds are indexes on the wire: **append, never insert or reorder.** After the original seven they run `VOTE`, `NPC`, `NPC_GONE`, `LAUNCH`, `RULES`, `DROP`, `TAKEN`, `HIT`, `AWARD`, `TOYS`, `JAIL`, each appended in its turn. `ArenaAwards.Medal` is an index on the wire inside AWARD and follows the same rule.

- **No message script preloads itself.** `arena_event.gd` and `arena_request.gd` are built with `new(kind, body)`, with an `_init` whose arguments default because dot-net's registry decodes with a bare `new()`. A self-preload in a `DotNetMessage` script loaded by a module inside a running `DotServer` was measured in mg-buses-from-hell as leaking the whole script graph at exit. `dedicated`'s last section reads every message script under `game/` as text and fails on one, because the leak is printed after `quit()` where no assertion can reach.
- **HIT goes to the attacker alone, AWARD to everybody.** `ArenaNetBridge._on_hit_confirmed` sums a tick's damage events per attacker and victim (a shotgun's pellets are one number), and `_flush_hits` sends them after the tick to `peer_for_session(attacker)`; a bot has no peer and is told nothing. AWARD is sent the moment the kill is judged, after its KILL, because the victim's screen names a nemesis from it ([client](client.md#kill-feedback)).
- **Nothing goes to a peer before its READY, and a READY before the seat is kept.** A client sends READY when its link says PLAYING, which the link decides itself after sending `loaded` on another ENet channel, so with loss the READY can reach the server before `add_player`. `mark_ready` used to answer it at once: a HELLO naming session 0 and a signon with no player of the peer's own, and nothing ever sends a HELLO again, so that client had a world and no body. It keeps the READY (`_ready_unseated`), `add_player` answers it, and `remove_peer` forgets one whose peer left unseated (peer ids are reused). `headless_net`'s ready gate sends the READY first and reads the HELLO back on a client bridge (armed: answered at once, it names session 0). The family's other bridges were fixed the same way (mg-deathrun 66fba36).
- **The KILL event carries an optional trailing critical bit** (`ArenaEvents.write_kill(..., critical)`); an older server's kill reads as none.

## Rules a client predicts with travel in RULES

A rule set on the server alone is a client that mispredicts every slide. `ArenaGame.set_movement_rules` keeps the changed keys (`movement_rules`), applies them to every player now and on `add_player`, and emits `movement_rules_changed`; the bridge sends `Kind.RULES` to everybody, and to a joiner straight after HELLO and before any JOIN. `ArenaPlayer.apply_movement_rules` writes the class base too, or the next class change would put the old number back. The same event carries what a client draws (`ArenaGame.SHOW_RULES`: body breaking, the surf air control) and the mode's catalogue index (`mode_index`, [client](client.md#a-client-knows-the-mode-only-for-display)).

The wall moves' keys ride the same set (`wall_run_*`, `wall_jump_*`, `wall_slide_speed`, [modes](modes.md#movement-is-a-games-choice)); `wall_jump_max_per_air` is a count, and `ArenaPlayer._set_rule` rounds it back to an int from the float32 RULES carries.

`headless_net`'s negative control for this is a fingerprint left apart by a server-only change, not a position gap: in this lockstep harness a snapshot corrects a wrong impulse within a tick or two. dot-player-controller's rewind used to keep the client's own launch cooldown and buttons; the timers and `previous_buttons` travel in `net_flags`.

**One exception, on purpose: a family cvar.** dot-combat's `mp_teammate_passthrough` is bound by the module with `FLAG_REPLICATED`, and dot-server sends it to the client's `DotClientLink` before the scene loads and on every change; `ArenaGame.follow_server_cvars(link)` keeps the world's combat manager on it and re-follows on the manager a map change builds. Six games bind the same cvar and all of them read it the same way, which RULES (arena's own event) could not give them. The server's side has the same trap: `change_map` builds a new manager, so `ArenaModule` re-applies dot-combat's cvars on `map_changed`, or a server on 0 or 2 was back on 1 from the second map. `dedicated` and `headless_lossy` check both, armed.

## Weapons over the wire

- **The owner's arsenal is filled from `net_carry`** (one bit per weapon, owner-only, for the ammunition's reason) through `ArenaContent.apply_carry` before the predictor replays, and `correct_ammo` follows. A loadout is resolved from a store on the server; without this a connected client's arsenal was empty for the whole match. `net_weapon` (everybody's) says which weapon is in hand, which a slot number cannot once there are several primaries in one slot.
- **A replayed tick fires nothing.** dot-net's predictor calls `_net_simulate` for a replayed tick exactly as for a fresh one. `ArenaPlayerNet._predict` wraps any tick at or below the newest one simulated in `begin_replay` / `end_replay`, and the rig's `used` is silent in a replay, or every correction re-plays the sound, the flash and the kick. **The movement is marked too**, with `DotFpsController.begin_replay`: unmarked, every replayed tick re-emitted the controller's signals and re-counted its statistics, and one wall run was heard six times over 20% loss ([history](history.md#the-wire)).
- **Projectiles**: `Kind.LAUNCH` carries who, which weapon, from where, how fast and the fuse. A client flies a copy through the same `ArenaProjectiles` against the same analytic map from `client_tick`; its copy decides nothing because its combat manager is not the authority. A mirroring client swaps its combat trace on a map change, or its copies bounce off the old map.

## Monsters are server-authoritative mirrors

`ArenaNpcNet` replicates each monster with dot-npc's `DotNpcNetSync` fields: never predicted, because a monster's position comes out of a navigation graph and a brain no client could reproduce. A client interpolates and draws ([horde](horde.md)).

## Bots

**One brain, solo and on a server.** `game/arena_bots.gd` feeds dot-bot's `DotBotBrain` from this game and turns its intent into the two commands a client sends. On a server, `ArenaNetBridge.add_bot` / `remove_bot` add an `ArenaPlayer` with no peer, registered with owner 0 so every client mirrors it, announced with a JOIN and a LEAVE like anybody, and `_commands()` writes what the bot presses into the same `last_move` / `last_fire` slot a client's input lands in, so the game ticks it exactly as a person. Offline, `ArenaClient._drive_bots` asks the same `ArenaBots.think` for each bot it added.

What the brain is told (`ArenaBots.World`, kept on the game as metadata): every player as a `DotBotContact` (position, velocity, view, health, team in a team mode), `combat.trace.line_of_sight`, the map's spawns as places to roam, a route between them (`World.route`: the horde's navigation graph when siege has one for this map, else `ArenaNpcs.nav_for` built once per map; on an imported map a dot-bot `DotBotNav` mesh baked from `ArenaMap.collision_root` in the background on the first route asked, empty (walk straight) until it lands, two to three seconds on the default surf maps), the held weapon's projectile speed (a `dot_weapon_projectile.gd` weapon's ballistics `speed`, 0 for anything else, so a rocket is led), a sound for every shot (`ArenaPlayer.used`) and who hit whom (`ArenaGame.hit_confirmed`, which makes a bot flinch and turn toward the shooter). Nothing else, so it cannot see through a wall.

**A grenade is the presses a person makes.** Arena has no throw key, so when the brain says `throw` (`bot_grenades`, a target that just went behind cover), `ArenaBots._throw` asks for slot 5, holds the trigger for `COOK_SEC` once it is drawn, lets go along the view the brain lobbed at, and asks for the slot it held before; `Mind.throw_stage` is where it is, and it gives up after `THROW_GIVE_UP_SEC`. `headless_bots` counts grenades apart from shots (a lob at a hidden target is meant to be blind) and checks each preset throws as its `bot_grenades` says. Its clock is the game's tick and its randomness is seeded from the bot's id.

**How well it plays is `bot_difficulty`** (easy, medium, hard, nightmare; medium by default) and the thirty `bot_*` settings each preset bundles (dot-bot's README has the table). `DotBotSettings.of(game)` holds them: the module binds them as cvars, the offline client as console variables (`ArenaClient._bind_bot_console`), with `-- --bot_difficulty <preset>` at launch. Solo, the Escape menu's General page has **Bot difficulty** (the saved setting `solo_bot_difficulty`, not `bot_difficulty`, which is dot-bot's console variable for the match in hand): applied at start unless the command line names one, and again whenever it is picked. A setting set by hand survives a preset change; `bot_settings` lists them, `bot_settings_reset` drops the hand-set ones.

How many is dot-server's `DotBotQuota` (`bot_quota` 4, `bot_quota_mode fill`, `bot_quota_empty 1`): `ArenaModule._keep_bots` corrects the count once a second through dot-bot's `DotBotRoster`, newest bot out first, so each person who joins takes a bot's place, and names each bot from dot-bot's pool (never a person's name, never "Bot 3"). `bot_quota_mode off` is a server with no bots. Needs dot-server API level 5 (`requires.json` is derived at packaging). Offline, `bot_quota` at the console is the same count (people + bots, so `bot_quota 4` is you and three bots) and `-- --bots N` sets the bots at launch.

**Solo used to be a test fixture**: `_drive_bots` faced the nearest player through any wall and held the trigger under 40 m, `headless_match`'s aimbot, and the first play test on Windows died twelve times in ninety seconds to it ([history](history.md)). `headless_match` still drives its own bots that way, because it wants kills fast and is not about how bots play; `headless_bots` is ([testing](testing.md#the-suites)).

## Inputs and the clock under real loss

- **Every input packet carries this tick's command and the ones before it** (`ArenaNetBridge.INPUT_COPIES`, 5 in all), and `receive_input` skips copies already simulated so they do not count as late. With one copy, a lost packet is a tick the server runs on the previous command; with three, 20% loss still left the server short now and then while the player turned. Two more copies are a few bytes each. `inputs_from` (per peer, in `describe()`) tells one client's uplink from another's.
- **The clock's round trip is ENet's own** (`ArenaNetBridge.link_rtt_ms(link)`, by duck typing because a web build has no ENet class), falling back to `ping_ms`. The heartbeat's ping is -1 for its first seconds, and until it answers the input lead leaves out the flight time and commands arrive after their ticks.
- **Lag compensation**: each command carries the client's view lag (`ArenaNetCommand.view_lag_q`, quarter ticks, only with a button down). The server records every player's position per tick (`ArenaGame._unlag_record`, a ring of 128, restarted on a jump over 10 m in a tick) and dot-combat's `rewind_fn` stands every other living player where the shooter drew them for the trace, then puts them back. `arena_max_unlag_ms` (1000, so 300-400 ms players are compensated; 0 is off) is the limit.

`headless_lossy` is the suite for all of this ([testing](testing.md#headless_lossy-real-enet-through-real-loss)).

## The map's toys

Each toy is an entity (`arena_toy_net.gd`: `state_transform`, `on`, `count`), registered by the server when the map's toys are built and named in TOYS (the map's id, then the net ids in toy order), sent to every ready peer and to a joiner at signon. **A client registers a mirror for every id the moment TOYS arrives**, under `ToyMirrors`, and hands each its toy by index once its own toys for that map exist: dot-net stops reading a snapshot at the first entity a client does not know, because a body cannot be skipped without its declarations, so a mirror missing while the client loads the map (or for good, on a client left on another map, as `headless_net`'s client 3 is) froze every player after it. A server's entities on the old map leave the registry and the tree at once on a map change.

## A frame's cost

A browser build has one thread, so a long frame is also a late read of the socket: it reads as a ping spike, the spike raises the input lead, and a longer lead makes every replay longer.

- **`cl_perf N` reports where a client's frame goes every N seconds** (`ArenaFrameProbe`, channel `arena.perf`): wall-clock frame times (not `delta`, which the engine clamps to eight ticks' worth, so a 450 ms frame read as 125 ms), the engine's process and physics times, the client's sections (`physics`, `predict`, `reconcile`, `snapshot` with the replays inside it as `replay_n`, `interpolate`, `bodies`, `present`, `hud`), and the round trip, lead and clock snaps beside them. Off unless asked for: `--cl_perf 5` on a desktop client, `?cl_perf=5` on the page, or `cl_perf 5` in the console. The sections are timed only while it is on.
- **The client reconciles once a frame, against the newest snapshot** (dot-net's `reconcile_once_per_frame`, set by name because a pack runs on whatever dot-net its shell carries). A stall right after the map loads (about 4 s in a browser) leaves a backlog on the socket; reconciling per snapshot, each one replayed up to the whole input history (129 ticks), so the next frame was longer and the next backlog bigger, and the client never recovered. Measured 2026-10-15 in a threadless web export, headless Chromium with software rendering, 10 bots, after the first 60 s: per snapshot, 144-200 ms a frame went into snapshots and 440-770 ticks were replayed a frame; once a frame, 5-40 ms and 20-105 ticks. `?cl_reconcile_per_snapshot=1` (or `--cl_reconcile_per_snapshot 1`) brings the old way back, so the two can be compared in one build under the same load.
- **A reconcile whose server state the prediction already reached is skipped** (dot-net's `skip_matching_replays`, set by name like the line above; it needs once-a-frame reconciling, because only then do the properties still hold the prediction when the snapshot is compared). Without it every snapshot replays the whole lead, about a round trip of ticks, so the round trip was in every frame's cost: `tools/client_bench.tscn` (a real client against a dedicated server with 3 bots through dot-net's relay, 15 ms of extra script a frame standing in for a slow device) measured 4.4 replayed ticks a frame at a 24 ms round trip, 10 at 120 ms and 17 at 230 ms, where the last also took the client from 59 fps to 49 (2.7 ms a frame reconciling, natively; a browser's script is several times slower). With the skip it is about one tick a frame at every round trip and 59 fps at all three: latency no longer reaches the frame rate. `?cl_replay_always=1` (or `--cl_replay_always 1`) turns it off for an A/B in one build.
- **`tools/client_bench.tscn` is the reproducible measurement**: `godot --headless --path . res://tools/client_bench.tscn -- --bots 3 --delay 50 --seconds 15 --burn 15`, with `--cl_replay_always 1`, `--off name,...` (stop a piece's `_process`), `--nodes` (what processes) and `--render` (lights, shadows, environment, meshes and materials: what a machine without a GPU can count but not time). Frame parts come from dot-menu's `DotMenuFrameClock`, the same clock `net_stat` draws.
- **What is left is not the network.** With the replays gone the frame in that harness was still 300-450 ms, most of it outside every timed section; software rendering at 1280x720 alone is 120-135 ms a frame in the same harness (dot-props' toys doc), and the measuring machine was loaded. A browser with a GPU is the measurement this still wants.
