# The client

`ArenaClient` is everything a person needs on top of `ArenaGame`, and a dedicated server never loads it: a camera rig, input sampling, the renderer, the HUD, the menus and the keys. How it predicts and draws between ticks is in [netcode](netcode.md#the-client-predicts-with-the-servers-collision).

## Booting and adopting a player

- **It watches `player_added`, not `player_spawned`.** `player_spawned` comes out of dot-match's respawn queue, which runs on the authority; a mirroring client never fires it. The symptom of waiting on it is the most misleading one here: the HUD binds by id and works, the scoreboard works, the connection is live, and there is no camera and no world, because both hang off that one reference.
- **Offline, the player is named before it is created** (`_start_offline`), which is the order HELLO and JOIN already give a networked client. Otherwise `_on_player_added` gives everybody it does not recognise a body, including the player the camera sits in, and their own nose is a pale slab across the bottom of every frame.
- **A spawn's yaw has to reach this client's sampler.** `DotFpsController.teleport` turns the controller's own sampler and the client samples with its own, so the next command overwrites the yaw. Offline the client turns its sampler on the player's `spawned`; connected, `_face_a_respawn` turns it to the nearest map spawn's yaw when its player is seen dead and then alive. Pits are deliberately not turned there, because they run inside prediction replays.
- **`ArenaHud.catch_up()`** fills the kill feed for a HUD built after kills happened, which is what a client joining a match in progress sees.

## A client knows the mode only for display

A client's `game.mode` is whatever it was built with. The server puts the mode's catalogue index in RULES (`ArenaGame._announce_mode` at setup and on every map change); a client keeps it as `shown_mode`, and `displayed_mode()` is what the keys and the banner ask. Its own `mode` is never replaced, because logic reads it. `props_on_e` read `game.mode` once and E launched instead of grabbing in the props modes.

## The mouse

**The client owns the mouse; `DotScreenStack.manage_mouse` is off.** dot-ui's stack forces CAPTURED whenever no screen is open, which is right on a desktop and impossible in a browser: pointer lock needs transient user activation, and a browser refuses it silently while `Input.mouse_mode` reads back CAPTURED. Two owners fighting is a cursor that flickers, so there is one, and it knows about the click.

## Keys

**Every key the client reads is a row of one table, `ArenaBindings`** (a dot-menu `DotMenuBindings`), read through its InputMap action (`Input.is_action_pressed` in `_read_fire` and the launch, `event.is_action` in `_unhandled_input`), never a keycode: movement (`dot_fps_*`, Duck labelled "Duck / slide", Walk on Alt), the dash (`dot_fps_sprint`, Shift), the launch (E), fire (Mouse 1), aim (Mouse 2), bash (F), reload (R), slots 1-5, previous and next weapon (Wheel up and Wheel down; see below), last weapon (Q), punt (G), the two chat keys (still stored as `chat_open_key` / `chat_team_key`, ACCOUNT scope, so nobody's binding reset), push to talk (V) and the held board (Tab). The InputMap, the settings document, the Controls page (a key button per row) and the help screen all read it; rebinding a taken key swaps, applies at once and is saved in the settings document. Before 2026-10-11 fire, aim, reload, the slots, the launch, the bash, the prop keys and push to talk were keycodes and the Controls page listed them as fixed.

**The wheel rows are named.** Godot numbers the wheel as mouse buttons 4 and 5, and dot-ui before API level 2 wrote them as "Mouse 4" / "Mouse 5", which a player reads as the thumb buttons; dot-ui level 2 writes "Wheel up" / "Wheel down" and still reads the old text. The rows are "Previous weapon" / "Next weapon" on Wheel up / Wheel down. The level-1 branch ("Mouse 4" defaults with "(wheel up)" in the label) was removed on 2026-10-12: the HUD names dot-ui's glance pieces (API 4), so `requires.floor.json` asks for dot-ui 4 and no shell below level 2 accepts the pack.

- **The props-mode remap follows the keys.** In a mode where players use props (`ArenaClient.props_on_e`) the Launch key grabs and drops a prop, the Bash key freezes it, and the launch moves to its own row (`arena_launch_props`, X; `launch_action()`). Not separate grab and freeze rows on E and F: two rows on one default are a conflict the table's swap cannot finish.
- **Right mouse aims** (zee's `ZeeViewModel.aim`) and F bashes; the `right_mouse_aims` setting (ACCOUNT scope) off makes the Aim key bash as well, and in a props mode the bash is the Aim key's whatever the setting says.
- **No noclip key.** dot-player-controller's `dot_fps_noclip` defaults to V, which is push to talk here; arena's noclip is an administrator's modifier, and the motor ignores the bit unless the server granted it, so `ArenaClient.make_sampler` takes the role off the sampler before the defaults are registered and V does one thing.
- **C slides as well as Duck** while Duck is on its default and no other row has C (`ArenaClient._add_slide_key`, deferred after any rebind, because the table re-applies the row after the setting changes; C is not a stored binding, so the swap cannot see it and the client takes it off Duck itself).
- Fire on Mouse 1 can be moved but not moved back by clicking (dot-menu's key button refuses the left button, which is how every button is clicked); "Reset keys to defaults" puts it back.

## The camera is written in exactly one place

`ArenaPlayer.present` writes the camera. Shake is handed to the player as `camera_offset` / `camera_roll` rather than written by whoever computed it; the weapon's view punch is added there too. dot-fx computes a displacement and touches no camera, so one implementation serves the play rig, a spectator's and a headless suite. `attach_camera` is idempotent and re-applies the field of view when called again, or a player who moves that slider sees nothing happen. Aiming scales the lens from the player's own field of view, never from the last zoom.

`field_of_view` is why dot-settings has `SERVER_CLAMPED`: a server may cap it (a wide view is a competitive advantage) but never reads it, because a server reading the field of view, the sensitivity, the bindings or the audio device would be assembling a fingerprint that survives a new account and every ban. A clamp is a bound: a player who prefers 90 keeps 90 under a cap of 100.

`viewmodel_fov` (horizontal at 4:3, default 65, 50 to 100, local and never clamped) is the lens the hands and gun are drawn through, separate from `field_of_view`: `ZeeViewModel.hands_fov` scales the view model in camera space by `tan(camera / 2) / tan(hands / 2)`, so the gun neither stretches when the world widens nor grows in a zoom. dot-menu declares it, draws the Video slider and applies it to every `ZeeViewModel` (group `dot_view_model`), so the game carries no code for it. `tools/render_fov.gd -- <fov> [<viewmodel_fov>]` renders a sniper and a rifle to `screenshots/fov/`.

**The camera's motion is dot-player-controller's arithmetic, written here.** `DotFpsView` is the addon's camera and this game does not use it (it writes the camera itself), so `ArenaPlayer.camera_motion` is a `DotFpsViewMotion`, the same cues without the view: `present` advances it once a frame from the drawn state and adds its roll, eye drop, nod and widening where it writes the camera. The landing reaches it from the controller's `landed` signal (never emitted in a replay), held until the drawn eye is on the floor (`_kick_landing`): the signal comes with the tick that lands, and the frames after it still draw the last of the fall, so kicked at once the dip added to the fall instead of following it. Christian's pick, `ArenaPlayer.camera_motion_picks`, judged on `tools/render_feel.sh landing strafe slide` and `render_wall_moves.sh` and measured by `headless_feel`:

| Cue | Pick | Why |
| --- | --- | --- |
| Landing dip | 6 cm at 16 m/s, from 8 m/s, recovering in 0.25 s, 1 degree nod | A spring kicked in velocity: the eye goes on down about 5 cm for 50 ms after a 5 m drop and comes back, never a frame's jump. Nothing under 8 m/s, so a plain hop (7.4 m/s) and a run of bunny hops dip nothing; a ledge, a launch or a long drop does. |
| Strafe roll | 1 degree at 9 m/s (the run), 8 a second, two stages; 1.5 more sliding | The genre's lean, small enough to read as motion and not as a tilted horizon; two stages so it eases in and out, reversing a strafe included (0.06 degrees a frame at most at 144 Hz). |
| Wall-run lean | 6 degrees away from the wall, 6 a second | As before. A drift into the wall leans toward it a fraction of a degree (0.5 at most on dm_atrium's run) before the lean away takes over: the strafe roll seeing the approach, not a wobble. |
| Bound | the rolls together at most 7 degrees | A strafe into a wall run cannot add up past it. |
| Widening | none up to the 9 m/s run, 4 degrees (vertical; about 5 at 4:3) by 15 m/s, 2 more sliding, 1 more on a wall, 4 a second, two stages | A plain run never changes the lens, so aim at a run is the player's field of view; a slide, a wall run, a dash or a hop chain open it a little. The aim's zoom multiplies the widened lens, from the player's own setting each frame, so nothing compounds. |

Each is a player's setting, 0 (off) to 2 times the pick: `camera_landing_dip`, `camera_strafe_roll`, `camera_wall_lean`, `camera_speed_fov`, ACCOUNT scope (motion sickness is about the person), in General > Camera motion and at the console. `ArenaPresentation.bind_camera_motion` pushes them when the client adopts its player and again on every change.

**A stair tread is eased into the eye** (2026-10-11): `ArenaPlayer._absorb_step` moves a stair step's share of the interpolated rise into `_step_offset`, which eases out over `step_smooth_time` (0.05 s). A tick is a step when it is grounded, rose more than the steepest walkable floor allows for the ground it crossed, and no more than `step_height`; a ramp's rise is steady and is drawn as it is. dot-player-controller's own camera has always done this (`DotFpsView.smooth_step_up`); this game writes its camera itself and had none of it, so the eye rose 16 cm in one frame at each tread of dm_box's stair at a run.

**Offline, a bot's body is drawn between its ticks** (`ArenaPlayer.interpolate_body`, set by the client for everybody but the player when offline): its node is where the tick put it, and the hitboxes hang off it, so `present` moves `body_mesh` to the controller's render state and blends the yaw. Drawn at the tick, every bot stood still on more than half the frames at 144 Hz and jumped on the rest, every frame 6 to 8 cm off its motion. A mirrored player is never this: dot-net's interpolator moves its node once a frame, and its controller is never ticked here, so the state it would blend from is not its own.

The death camera is driven once a frame, not once a tick ([modes](modes.md#spectating)). The client hands dot-spectate the level (`camera_world`, `camera_mask` = the `world` and `prop` layers) the first time it drives a spectator camera, so the chase and death cameras are pulled out of walls, and a death camera whose killer the level hides stands back from the body on the open side and looks at it (dot-spectate; the first play test had a death camera that was a frame of a teal wall).

**Third person** (F5, `ArenaBindings.VIEW`, under the server's `mp_forceview`: dot-player-controller's `DotPlayerViewRules`, bound REPLICATED by the module and followed through the link). `ArenaPlayer.present` writes the first-person camera as always, then `_place_third_person` sweeps it from the eye to `THIRD_PERSON_OFFSET` (right, up, back) through a dot-core `DotCameraProbe` and draws the body on the drawn feet; the view model is hidden and the held weapon shown. A player with no site avatar is drawn as the stock figure everybody else sees. A `DotCameraFade` under the camera is handed the other figures (`_other_figures`): players are solid (`mp_solidplayers`, [netcode](netcode.md#players-are-solid-to-each-other)) and stop two radii apart, which still puts a face inside the near plane, so the fade hides one at the lens and, in third person, fades one between the camera and you. `tools/render_cameras.sh [map]` flies both cameras round every spawn (armed: fails if the unprotected camera never went into a wall, or the probed one did) and draws the worst frame before and after; `tools/render_views.gd` draws the real client in both views and under `mp_forceview 1`.

## The presentation layer

`ArenaPresentation` holds dot-settings, dot-audio, dot-fx and dot-console on the client. What was missing for a long time was never the files; it was the decision about what is audible, how many at once, how loud, and how far away it stops mattering, which is a document:

- Every weapon sound is positional with a real cull distance, because a shot you cannot place is a shot you cannot answer. A hit marker is flat: it is information about your own shot.
- `max_concurrent` is 3 on a rifle. Twelve in one tick is one gunshot twelve times as loud, with comb filtering.
- The shot is predicted on the client that fired it. Safe because a sound never changes the simulation: a shot the server later refuses cost a noise.
- **No audio files ship.** The catalogue names paths in `audio/` that do not exist; `sound_recipes()` maps each id to a `DotAudioSynth` voice and `DotAudioSinkGodot` falls through to that bank. Weapons get different voices on purpose: hearing somebody's shot is knowing what they hold. Dropping in real files switches the stand-ins off one id at a time. zee-dot-weapons brings its own baked reports; these are only what a client shell too old to carry `ZeeShotFx` falls back to.

- The local player's wall moves have their own stand-ins, flat and theirs only: `wall_run` (a step, pitched up) as a run starts and `wall_jump` (an impact, pitched up) on a kick off a wall, from `DotFpsController.wall_run_changed` / `wall_jumped`, which a replay does not emit ([netcode](netcode.md#weapons-over-the-wire)).

**dot-effects and dot-fx are different things and this game has both.** `ArenaEffects` is burning, slows, invulnerability: things that change the simulation. `ArenaPresentation` is what they look like, and never changes the simulation, which is what lets a frame budget drop one.

### Effect scenes

`scenes/fx/` holds `muzzle_flash`, `impact_spark`, `bullet_hole`, `death_burst` and `explosion`, plain scenes with no script and no external resource, so a delivered pack has no path inside them to rewrite. `CPUParticles3D` rather than GPU so headless and Dummy renderers run them like anything else. dot-fx refuses a missing scene silently at DEBUG (a client whose pack is still arriving legitimately asks for scenes it lacks), so `_build_fx` warns when one is missing and `headless_presentation` asserts `missing_scenes()` is empty.

- **Every effect is built against one frame, `ArenaPresentation.facing(at, direction)`: -Z along the shot.** A `DotShot` carries no surface normal, so the hole's decal projects along the shot, which lands it on a wall, a floor or a ceiling alike.
- `ArenaPresentation.on_used(outcome)` is the loop, so the suite drives the exact path. The flash is placed `MUZZLE_OFFSET` along the aim and a little below and right, because a shot starts at the eye.
- The explosion is its own scene; reusing the death burst read as somebody dying.
- The death burst is dark-red droplets (small spheres that fall and shrink) under a short soft mist, about a second, because the ragdoll is the body now; it was 24 flat red cubes 12 cm across, which the first play test showed as debris. `--fx` adds `<map>_fx_death_near`, the burst from four metres.
- A one-shot shorter than a frame is not drawn (`CPUParticles3D` ages it by the first frame's whole delta). Irrelevant at 60 fps; it is why `--fx` renders slow the particles.

## Escape, the pointer and the menu

- **The menu is dot-menu's `DotMenu`** (`ArenaMenus.build`), the same one every other game has: dot-menu's stock General, Video, Audio, Controls and Advanced pages as views of `ArenaPresentation.settings`, plus this game's Interface page (theme, frame-rate counter, crosshair, `hud_safe_area`), its rows on the stock pages (view model, push to talk, `invert_pitch`, `right_mouse_aims`) and a Servers page. Converted from dot-ui's `DotPauseScreen` and two `DotSettingsScreen`s on 2026-10-10 ([history](history.md)).
- **First Escape releases the cursor, the second opens the menu; a click captures.** Escape is how a browser exits pointer lock and it refuses to re-enter for about a second. So `open_on_escape` and `manage_pointer` are off and the client stays the one owner of the pointer (`_apply_mouse`); `overlays_changed` gives it back when the menu, its help or the console closes. Escape still closes the menu.
- **While the menu is up, `_unhandled_input` acts on nothing**: dot-menu owns every key then, and a number key behind a menu must not switch weapons.
- **Leave is dot-menu's stock one** (`leave_on_its_own`): connected, it disconnects the client link and the shell goes back to its own menu; solo on a desktop it quits. `leave_requested` is still emitted for an embedder; until 2026-10-11 it was all Leave did, and nothing listened.
- **H opens help** (`ArenaBindings` has dot-menu's help row; `ArenaMenus.fill_help` writes the goal and lists every mode from `ArenaModes`). The HUD's key hints list H, so dot-menu's corner plate is off here; nothing else in the table may default to H. `headless_presentation` checks it.
- **B opens the loadout** (dot-menu's `DotMenuLoadout`, `dot_menu_loadout` in `ArenaBindings`, guarded on the host's dot-menu 6 and dot-loadout 2): primary, secondary, melee, grenades and gear as cards with the HUD's weapon silhouettes and zee's `ZeeWeaponCards` numbers (`ArenaClient.decorate_loadout_choice`). Solo `loadout_offer` / `choose_loadout` ask the game's own `ArenaGame.loadout_command`; connected the server's (`/loadout` and the `loadout_menu` notice). A choice is in the player's hands at once in warmup or spawn protection (`ArenaGame.rearm_if_allowed`) and otherwise at the next spawn, and the toast says which. A mode that hands out the weapons (gun game, Only Snipers) closes it with that reason (`loadout_closed_reason`), and the key hint goes. The choice is remembered on this device and re-sent on the next join (`_restore_loadout`), never under scratch settings. Christian's first play test asked for it; the owner's side is in [modes](modes.md#loadouts-and-the-owners-rules).
- **M opens the map menu** (dot-menu's `DotMenuMaps`, `dot_menu_maps` in `ArenaBindings`). Solo, `ArenaClient.map_menu_rows()` lists `map:<id>` rows (every map that can host the mode being played) and `mode:<id>` rows (every mode the map being played can host), in the ballot's ids so a server's list reads the same, and `change_from_menu()` changes through `ArenaGame.change_map` and rebuilds the level as a server's change would (`_on_map_changed`). On a server the list and the change are dot-vote's `DotVoteMapMenu` over this game's ballot (`ArenaVoteSource`): it changes through the map director for a player holding the owner's `sv_map_menu_flag` and gives anybody else a nomination and a rock-the-vote; a row no longer offered is refused with the reason ([services](services.md#the-map-vote)). No other row in the table may default to M; `headless_presentation` and `dedicated` check it.
- **The crosshair fades out down the sights**: `ArenaHud.present_body` hands dot-ui's `DotCrosshair.set_aim` the view model's `aim_fraction` (guarded on dot-ui 5); hip fire keeps it, a scope hides it for its own reticle as before.
- **Servers is a page**, drawn fresh from dot-browser's listing each time it is shown, with a Refresh and a Join per server; it is left out of the sidebar when the browser did not come up. Join closes the menu and goes through `ArenaBrowser.join_requested` ([services](services.md)).
- **`ui_theme` colours the menus and the board, not the HUD**: the HUD is this game's own drawing.
- **dot-menu's stock video settings are declared** (`DotMenuStock.declare` with the video and interface groups) and applied by the client's `DotMenuApplier`, which is also bound to the presentation's mixer and fx so a row moved in the menu lands with no Apply. The keys this game declared first keep its defaults (a field of view of 100, horizontal at 4:3). Its invert is `invert_pitch`, stored before dot-menu's `invert_mouse` existed, so the stock invert row is not drawn and this game adds its own.
- **The old Interface screen is gone, not moved.** It edited a `DotUiConfig` that nothing saved and nothing read after the HUD was built (scale, transition time, line counts), so its rows changed nothing. The one that matters is `hud_safe_area`, a real setting now, applied live (`ArenaHud.set_safe_area`).
- **The Tab scoreboard is the menu's `DotMenuScoreboard`, held** (`scoreboard_action` is `arena_scoreboard`). K, D, A, Score, then Time and Ping; rows from dot-match sorted by rank (`ArenaMenus.Board`); on a connected client the server's roster (`DotClientLink.want_scoreboard`, sent only while Tab is held) is merged by player key; offline an empty source is pulled twice a second so the rows stay live. A team mode groups rows under the sides. Offline, Time and Ping read "-". The end of a match opens it and the next match closes it (`_summary_board_open`). `Board` is handed the game and reads `match_node.scoreboard` on every draw: it was built before the match node existed and held a null, so a connected client drew only the roster (the local player, K and D as dashes); a mode change also builds a new match node. Known gap: a connected client's records carry no kills, deaths or score (nothing replicates them), so the board and the HUD's scores read 0.
- `sensitivity`, `invert_pitch` and `crosshair` are pushed by `ArenaPresentation.bind_look` / `bind_crosshair` at bind time as well as on `changed` (a loaded value has not changed), and again when the sampler gets its player's tunables, a new object carrying the default. Sensitivity is 0.022 degrees per count, the same as game-g2gfast, because it is an ACCOUNT setting in the shared namespace.

## The HUD

**Laid out for a glance** (`ArenaHudGlance`, the 2026-10-10 reference study): the two scores either side of the clock at the top centre with "First to N" and the mode under them, and a ranked row of portraits with kill counts under that; the kill feed top right (killer, the weapon's silhouette, a headshot mark, victim; a gold edge on a line you are in; names cut at 14 characters so a line never reaches the portraits at 1280 wide); health bottom left as a bar with its number, armour as a thin bar under it when there is any; `magazine | reserve` under the weapon's name bottom right; the carried weapons as silhouettes stacked on it, bottom up, with their slot keys; slide, launch, dash and the wall jump as buttons bottom centre, each with its key, a cooldown that darkens the button from the top and counts down, a gold edge while in use, and the wall jump's jumps left in the air as pips; key hints on the left beside the streak meter; a context prompt ("Cancel slide [C]", "Reload [R]") left of centre. The challenge and the coins moved to the top left, the notice and the death panel under the portraits.

- **Half the pieces are dot-ui's glance pieces** (since 2026-10-11, dot-ui `docs/hud.md`, "The glance pieces"): health (`DotVitals`, which draws its own bars), ammunition (`DotAmmoCounter`), the scores and clock (`DotScoreStrip`; its `clock_text` rounds up, so the clock never says 0:00 with time left, where arena's own rounded down), the prompt (`DotKeyPrompt`), the key hints (`DotKeyHints`), the hit marker and the damage numbers. They were arena's and moved once other games drew their own. Arena's own are the portraits, the kill feed with its silhouettes, the weapon slots, the ability bar, the medals and the streak meter (`ArenaHudGlance`, `ArenaHud`). This is why the pack asks a shell for dot-ui 4 (`requires.floor.json`): a class name cannot be guarded by a level check.
- **Every piece draws from plain values it is handed** (`show_*`) and knows nothing of a player or a match; `ArenaHud.present_scores`, `present_portraits`, `present_gear`, `present_abilities` read the game and hand them over. A suite or a render tool can drive one piece alone.
- **Readable over a pale map**: bold text with a dark outline everywhere and a dark translucent plate under each group. The first HUD drew thin regular-weight text straight over white tiles and health, ammunition and the key hints all but vanished.
- **Dark by default, in the menu's theme, live.** Christian's first play test (2026-10-11) found the HUD too toy-like (white key caps, saturated blue buttons and score plates, white medal rings) and asked for a darker default that dot-menu's themes can change. `ArenaClient` hands the HUD to `DotMenu.follow_hud` with `ArenaHud.accent_theme()` (arena's gold as `highlight`, nothing else), so the menu sets the theme on the HUD now and at every theme change, and the `hud_scale` setting reaches `DotHud.user_scale`. dot-ui's pieces read their colours from that theme; arena's own pieces read the same names through `ArenaHudGlance.Ink.c` (plate, edge, text, dim, ink, key caps) and blend their own saturated parts (the ability buttons, a medal's ring) by `Ink.bright` (dot-ui's `team_fill`: dark under Midnight, the first bright look under "Arcade"). Nothing in the HUD is a literal colour that a theme should change; the side colours, medal colours and weapon art stay the game's. `tools/screenshot.sh <map> --glance --theme <id>` renders a theme, `--hud-scale <k>` a size; `headless_presentation` checks the default is dark and that a theme change and the size reach both kinds of piece.
- **In a team mode** the strip's plates are the sides (yours on the left), the feed's names and the portraits' rings are in the side's colour. In a free-for-all the left plate is you and the right whoever is ahead of you, or behind when you lead.
- **Portraits are rendered people** (`PortraitCache`): the head of the person each player's avatar is drawn as (`ArenaAvatars.look_of`), in a 96-pixel viewport of its own, rendered once (`UPDATE_ONCE`) and again only when the avatar's digest changes. The kit faces -Z, so the camera is on that side. Nothing is built without a display: suites draw initials.
- **Weapon silhouettes are generated** from zee's models by `tools/build_weapon_icons.sh` into `assets/weapon_icons/<id>.png` (white, barrel right, 48 px high, mipmapped). Drawn from a 600-pixel render at a tenth of the size, the thin parts broke into dashes; a missing icon draws the weapon's name. The ability icons are Kenney's (`assets/hud_icons/`, named by ability id).
- **The keys the HUD names are the player's**: `ArenaClient._hud_keys` fills `ArenaHud.keys` (launch, reload, the slots' keycaps and the rest) from `ArenaBindings` at boot and after a rebind; Slide says C while C is Duck's second key.
- `hud_safe_area` (Interface page) is the HUD's margin, applied live (`ArenaHud.set_safe_area`).
- `ArenaHud._make_label` grows both ways: a centre-top preset is a zero-width box and a wider `Label` grows by `grow_horizontal`, which defaults to END.
- `ArenaHud.match_view` reads the camera's own `fov` each frame for the crosshair's spread, because the camera is where the slider, a server clamp and the first `attach_camera` all end.
- **The red edge is a shader** (`ArenaHud.HURT_SHADER` on a `ColorRect`), computed per pixel in the screen's own ellipse with a dither against banding: strongest at no health and gone above `HURT_FROM`, plus a pulse on every hit that is dot-fx's `hurt_flash` drawn (`flash_source`, so the player's "no flashes" and the rate limit hold; nothing drew that flash before). It was a 64-pixel `GradientTexture2D` stretched to the screen, in visible steps at 1080p in the first play test.
- Words agree with numbers: "+1 coin", "5 coins" (`coins_text`); a challenge's progress reads in its own units, "0:03 of 10 h", "2 of 100k", "11/100" (`progress_text`), never the raw counter over a six-digit target, which the play test read as a debug string.
- Full-screen overlays (the blind, the low-health edge, the scope) are sized to the viewport, not to the HUD: `DotHud` insets itself by the safe area and the first renders left a frame of world round the edge. The blind sits under the HUD's widgets so the clock and kill feed still show.
- `ArenaHud.notice` is a centre line held four seconds: chat lines, map-change notices, the mode banner, the end-of-match MVP. It wraps to two lines at most, `notice_width(frame)` wide: clear of the client shell's 360 px ballot column on the right, because the server's "Vote: …" line as a ballot opens ran one unbroken line off the right edge, behind that ballot. While a ballot is drawn (`covered_rect`, below) dot-vote's opening list ("Vote: a, b (20s)", `is_ballot_line`) is not printed at all and is taken down if it came first: it was the ballot's own rows again, two lines deep over the medals. dot-server's yes/no line ("… type !yes or !no") still is, since it says how to answer.
- **The right edge from 110 px down is the client shell's**: its ballots and lines are one column there, a third of the frame wide (240..360 px; dot-server-deploy's `client/notice_overlay.gd`). The game cannot see when a ballot is open, so it stays clear always: the kill feed is as many rows as end above 110 px (`feed_lines_clear`: three at the 16 px safe area, fewer with a larger one), the key hints are on the left, and the weapons sit on the ammunition counter, which keeps five below a six-row ballot at 1280x720. Before 2026-10-11 the feed's fourth and fifth rows, the hints and slot 1 were under the ballot at 1280x720 and 1600x900. Judge it with `screenshot.sh <map> --glance --ballot`.
- **The weapon slots make room for a ballot that comes down over them.** This game's own map vote is seven rows (six maps and Extend) and reaches y 437 at 1280x720, over slots 1 and 2 of five, which the bottom-up stack alone could not clear. `ArenaHud.make_room` reads every visible Control in dot-ui's `dot_hud_cover` group each frame (`DotHudPiece.covered_rect`, merged, in the HUD's own space) and hands the cover's bottom to `WeaponSlots`, which tightens its pitch from 40 to no less than 30 px with the bottom row fixed on the ammunition counter, then shows only the run of rows around the current slot. Every row and the full pitch come back the frame the ballot goes. dot-ui's pieces dim themselves under a cover that meets their own footprint (`cover_mode`), each cover tested alone. Judge it with `screenshot.sh <map> --glance --map-ballot` (the seven-row stand-in).
- **Below 1280x720 the whole HUD is scaled, never laid out again** (dot-ui's `DotHud.fit_design`, set to `ArenaHud.DESIGN_FRAME` in `_init`: `fit_scale` is the short side's share of 1280x720, 1 from there up, never under `fit_min`, a half; `fit_to_frame` places it and the viewport's `size_changed` refits it). Arena found this and dot-ui took it over (API 4). Standalone at 854x480 the challenge ran over the scores, the ability bar and "Cancel slide" over the health and the medals over the portraits; at 960x720 the scores reached the kill feed. The client shell draws on a 1280x720 canvas stretched to its window, so a game in the shell never sees a smaller frame: scaling is the same answer for the game on its own, and 1280x720 and up are drawn exactly as before. Re-laying pieces out per size, or dropping some below a width, was the alternative; one scale keeps every piece and every distance between them, the shell-column clearance included (it is in the HUD's own units). Each piece says where it draws (`footprint()`, collected by `ArenaHud.footprints()` in frame pixels), and `headless_presentation` puts every piece up at once on five frames from 720x1280 to 1600x900 and fails if any two meet; a new piece needs a `footprint()` or it is not checked.
- Also drawn: the kill feedback (below), "HEADSHOT!" over the victim, the death panel (with the server's nemesis), coins, and a health bar over a hurt enemy for three seconds (two quads turned to the camera each frame).

## Kill feedback

What makes a kill feel like one, laid out the way the genre's best-liked shooters do it: a hit marker, damage numbers, medals, a killstreak meter and "+points  Victim". All of it is `ArenaHud` (dot-ui's `DotHitMarker` and `DotDamageNumbers`, which advance themselves; arena's `MedalRow`, `StreakMeter`, `popup`), drawn with no art except the medal icons, which are Kenney's CC0 icons in `assets/medals/` loaded through `ArenaPaths.rebase` (a missing icon draws the badge without it).

- **The server decides all of it; the client draws.** `ArenaGame.hit_confirmed` (every damage event a player dealt) becomes one `HIT` per victim per tick, sent to the attacker alone; `ArenaGame.medals_awarded` becomes an `AWARD` to everybody, straight after the KILL it belongs to ([netcode](netcode.md#events-and-requests)). Offline the client connects the same two signals, since its game is the authority. The rules are `ArenaAwards.MedalBook` ([services](services.md#progression)).
- **The hit marker waits for the server**, a round trip after the shot. It used to sound on the client's own predicted `shot.damages`, which a server may refuse (a lag-compensated miss, a protected spawn), so it said "hit" about shots that did nothing. The shot's bang, flash and kick stay predicted: they say "I fired", which is true either way.
- **The client keeps no ledger of who killed whom.** Revenge and the nemesis line used to be counted on each client from KILL events, which a late joiner starts empty and one missed event puts out of step. The HUD's `nemeses` is written only from AWARD.
- **The same HIT draws the hit on the body** (`ArenaClient._draw_body_hit`, zee's `ZeeShotFx.play_body_hit`, through `has_method` for an older shell): the presentation ray already bursts red on a body it meets, and this covers a lag-compensated hit on a body that has since moved; zee skips a second burst within a fifth of a second.
- The hit marker is four ticks round the crosshair, white (cream for a headshot), red and larger on a lethal hit; a pellet landing after the lethal one does not turn it white again. Damage numbers rise from the server's hit point, projected through the camera every frame; hits on one victim within 0.35 s add into one number; gold for a headshot. A hit with no point (a blast) rises from the victim's chest.
- Medals are a row above the crosshair: a deep disc rimmed in the medal's colour with its icon lit in the colour (a white-ringed coloured badge under the bright theme) and the name, scaling in past full size and back, holding about 2.4 s, fading; several from one kill come in 0.14 s apart, as do their sounds (`ArenaPresentation.on_medals`). Double, Triple and Multi Kill carry a 2, 3 or 4+ on the badge.
- "+points  Victim" sits level with the crosshair, to its right, and holds 2.6 s: above it, it was drawn over the number of the shot that killed (rendered).
- The killstreak meter is a thin gold bar up the left edge with a flame over it and "Killstreak xN" under it. Its count is the server's streak from AWARD, and KILL events end it on a death. It is 180 tall so its words end above a full chat log (eight rows reach y 424 at 1280x720); at 250 the sixth line of chat wrote over "Killstreak xN" in the client shell, where a ballot's "Vote: …" line wraps to two. `headless_presentation` checks the two apart.
- Every medal is a dot-audio id (`medal_<name>`) and a lethal hit is `kill_confirmed`; until recordings exist each is a `DotAudioSynth` voice at its own pitch (`MEDAL_VOICES`).
- **No Scope reads the aim button**: the weapon command carries it as `ArenaPlayer.BUTTON_AIM` (`DotWeaponCommand.BUTTON_USER_0`, read by no addon) and `ArenaPlayer.aiming` records it on the server. It is a claim like every button, and since aiming changes nothing the server simulates, a client that lies about it earns a medal and nothing else.

## The chat box

A chat box is a HUD widget, not a `DotScreen`: a screen is modal and takes the display, a chat box is eight lines in a corner that leaves the game visible. It is dot-ui's `DotChatWindow`, built by `ArenaPresentation` beside the console.

- `chat_window` (`auto` / `on` / `off`), `chat_open_key` (Y) and `chat_team_key` (U), all ACCOUNT-scoped. Off never means out of the conversation: the log keeps drawing; the setting decides whether there is anywhere to type.
- `auto` is answered by the server: `ArenaServices` points `DotChatManager.watch_relay` at its relay, dot-server tells each joining client, and `ArenaClientExtras` turns that into `chat_relay_changed`. A client cannot know on its own whether its room also exists on a web page.
- **`ArenaPresentation.swallows_input()` covers the box as well as the console**, or typing walks the player.
- **The console is dot-console's `DotConsoleKit`**, with `quit`, `audio`, `fx` and `where` added before the server's console. It is built after the menu (`ArenaPresentation.build_console(menu)`), so the kit registers it as one of the menu's overlays and the sampler is suspended by dot-game's `DotGameClient` (`platform`): its `busy_fn` (`_input_busy`: the console, the chat box, any menu) and its cover are polled every frame and `input_blocked_changed` calls `_suspend_input`. `headless_presentation` holds a key down to prove it (it waits two frames: the platform polls in `_process`).
- **The platform layer is only partly taken.** `ArenaClient._build_platform` adds `DotGameClient` first and takes its load gate (the map hold and the weapon warm-up are put on `platform.gate`), `link`/`offline`, the browser flush and the input-blocked signal. `use_settings`, `use_console`, `capture_pointer` and the Tab board are off on purpose: the settings are `ArenaPresentation`'s plain manager with the menu built round it by `ArenaMenus` (Servers page, camera rows), the console must come after that menu, Escape releases then opens and "Click to play" is arena's, and `ArenaMenus.Board` merges dot-match's records with the roster.
- **`DotFpsSampler.suspended` is set on `opened` and cleared on `closed`.** Movement is polled every physics frame regardless of what consumed an event, so `swallows_input` alone is not enough.
- **Scaled with the HUD.** The box sits in a `ChatScreen` control sized frame / `ArenaHud.fit_scale` and scaled by it (`ArenaPresentation.fit_chat_screen`, refitted when the viewport moves), so below 1280x720 it shrinks exactly as the HUD does; unscaled, a full log at 854x480 reached the killstreak meter, the key hints and the slide prompt. It is 340 wide, not dot-ui's 460, because the slide prompt starts at x 381 inside a full log's rows. `headless_presentation` lays both out at five frames and checks the log against every `footprint()`; `screenshot.sh dm_box --glance --chat` (with `RESOLUTION=854x480`) draws a full log.
- A line reaches the client on `DotClientLink.chat_received` (dot-server's wire), and `ArenaClientExtras.receive_wire` hands it to `DotChatClient`, which refuses a dictionary with no `m` so the fallback draws it.

## Avatars

**Players and bots are drawn as dot-player-char's people** (`DotHumanoidFigure`, its [docs/people.md](../../dot-player-char/docs/people.md)): four animated CC0 bodies on one rig, the family's one style for players, bots and NPCs, coloured by a look. The avatar **document** is still this game's (`arena_stock`: body, head, crest, a tint each), because it is what a server validates, what the site's avatar translates into (`from_site`) and what stored profiles hold; `ArenaAvatars.look_of(avatar, key)` turns it into a look. A Kenney body part gives that skin's clothes, a Kenney head that skin's face, hair and which of the four bodies; a primitive part gives its tint to the top over a stock person seeded by the storage key. The crest is its own model on the person's crown (`ArenaAvatars.crest_of`, hung on `attachment(&"crest")`, the mount on the head bone), so it crouches and nods with the head; the view's pitch goes to the figure as `aim`. With no art (a build without dot-player-char's `people/`) the figure is the capsule.

`ArenaPlayer._animate_figure` tells the person how the drawn state moves (on the floor, vertical speed, crouched, swimming, on a ladder, alive) and what the hand holds (`def.slot`: melee, thrown, or a gun), and a melee use swings over the legs. The gun hangs on the person's own hand (`attachment` forwards to the figure), which is the **left** hand: the kit's gun clips are left-handed. The HUD portraits are the same person's head (`PortraitCache`).

A critical takes a limb off the skin (dot-player-char bakes it out and shrinks its bones to the stump) and `_mend_body` calls `figure.mend()` on respawn; the ragdoll falls by the person's bones.

`avatars/arena_{body,head}_kenney_<a..r>.tscn` are 18 characters from the CC0 character kit, generated by `tools/build_avatar_parts.gd` out of `avatars/kenney/`. They are now only the parts the document names (and what the horde's monsters wear, [horde](horde.md#figures)); nothing draws a player with them. The two primitives stay at the front of `BODIES` and `HEADS`, because `[0]` is the schema's default and must resolve without the art.

**A stock avatar chooses each slot from its own mix of the key's hash** (`ArenaAvatars._pick`, a 32-bit integer finaliser with a per-slot salt, so it agrees on every machine). Server ids are consecutive and a string hash moves by a few per id, so the first version's `(seed / 7) % HEADS.size()` dressed players 112..118 in one head: a row of the same face in the world and in the portrait row. `headless_presentation` checks 16 consecutive ids for at least 8 heads; the old pick gave 4.

**Your own body in first person** (`arena_fp_body`, off by default) builds the local player a body with its head bone shrunk to nothing (`hide_head`: the person is one mesh, so dot-player-char's hide-by-name has nothing to choose from) and draws it `FIRST_PERSON_BACK` behind the eye.

**Third person is deliberately not here.** The movement is analytic and lag-compensated, and server and clients agree because there is exactly one motor to agree about. game-playground is where third person runs.

## The end of a match: final killcam, winner, scoreboard

When the match ends every client plays, in order, the final killcam, the winner reveal and the scoreboard. `ArenaKillcam` (`game/arena_killcam.gd`) puts every drawn frame (each player's feet, look, life and eye height, as presented) and every kill into dot-replay's `DotKillcamBuffer`, which needs no new traffic; at the end it hands the last kill to `DotKillcam`, places the bodies and puts its own camera at the killer's eye. The length is the server's `mp_killcam_time` (RULES `killcam`, default 7, 0 off), and the authority adds it to the mode's `match_end_sec`, so the server never waits on a client. Then dot-ui's `DotWinnerReveal` names the winner ("MATCH MVP" in a team mode) over a podium of the top three, then the scoreboard opens. Both hide the HUD and the view model, both skip on jump, fire or Escape, and leaving the end state skips whatever is still up. The player setting `reduce_motion` (General, Camera motion) shows the reveal's final frame at once. Look at it with `tools/render_killcam.sh [map] [--reduce-motion]`.

## Footsteps and the bed

- **Footsteps and a bed per map are dot-audio's stock.** `ArenaPresentation.keep_walkers` keeps every player's steps; a step is grounded by a ray, because a mirrored player's controller is never ticked on a client, so its own grounded flag says nothing. `bed_for` picks the map's ambient bed by map prefix.
- **Levels are measured, not judged by ear**: `addons/dot_audio/tools/loudness.sh --warmup=6 --fire` (the −17 LUFS band; `loudness_trim_db` is the trim), which drives the local player through `tools/loudness_pilot.gd`. A run whose `capture pilot:` line shows no walking measured the bots, not the game.
- Stock ids have files, so the stand-in check skips them.

## Looking at it

No assertion sees the screen. Render and look after any change to the client, a menu or a map:

- `tools/screenshot.sh <map>` renders a map from three angles into `screenshots/`, a built-in map under its own lighting document exactly as the client draws it; `RENDERER=gl_compatibility` renders what the client shell draws ([maps](maps.md#colour-and-light)); `--view <name> <from> <at>` adds a frame, `--admin` the beacon and blind, `--fx <eye> <aim>` six shots and a death, `--feel` the HUD, scope, drops, body breaking and `<map>_feel_kill` (medals, "+points", the streak meter, the hit marker and two damage numbers in one frame; the HUD animates in real time and a frame takes about 70 ms, so a shot's `late` stages put each piece up a few frames before the grab). On an imported map it plays a short deathmatch first and adds player, ramp, water and booster frames.
- `tools/screenshot_menus.sh` renders every page of the Escape menu (`menu_<page>.png`, Servers with two fixture servers), the help screen, the Tab board, the HUD with the chat box, and the console open (`hud_console.png`); compare them with game-playground's `menu_*.png`. The chat box sits at `margin_bottom = 110` to clear health and armour, and only the picture can say whether 110 is right. It refuses to save a grey rectangle when a `push` fails.
- `tools/screenshot.sh <map> --glance [tdm]` is the whole HUD over a real match: an `ArenaGame` with eight players and kills filed through dot-match, the local player's hands, abilities charging, a slide on, medals and a hit staged late. It is how the HUD's layout is judged: render it at `RESOLUTION=1280x960`, `854x480` and `720x1280` as well as the default 1600x900, and with `RENDERER=gl_compatibility`; `SHOT_SUFFIX` names a run's frames apart. `--glance --ballot` adds a stand-in for the client shell's drawn game ballot, placed as dot-server-deploy's `client/notice_overlay.gd` places it (a copy: keep it in step; the shell hides the vote's HUD line while its ballot is open), and the centre-printed "Vote: …" line; render it at a desktop and a narrow size (`RESOLUTION=854x480`). Below 1280x720 the stand-in is scaled by the HUD's own factor, as the shell's canvas is.
- `tools/render_loadout.gd` (`xvfb-run -a godot --path . --resolution 1280x720 --script tools/render_loadout.gd`) opens the offline client's B menu on the primaries, over budget, on the grenades, closes it with a new primary (warmup: in hand), then frames the crosshair at the hip, raising, aimed and through a scope, into `screenshots/loadout/`, with a line per check.
- `tools/play_online.tscn` (`xvfb-run -a godot --path . res://tools/play_online.tscn -- --seconds 56 --vote-at 40`) is a real connected session: a dedicated server in a child process with the module's bots and map vote, the real client over ENet, a pilot that runs and shoots, a frame every 4 s into `screenshots/online/`. The shell's ballot panel is not drawn (the shell is not here), so the ballot is judged on the server's log, not a frame. Under load the client can take 30 s to be alive; the tool waits for it.
- `tools/build_weapon_icons.sh` regenerates the weapon silhouettes; commit the PNGs.
- `tools/screenshot_weapons.sh` plays the offline client through its own input path. It stages one bot four metres in front of the player, three-quarter on and in the open (by the map's trace), and writes that bot's commands itself: `_drive_bots` skips a bot carrying the `bot_scripted` meta. Turning toward the nearest bot instead photographed a wall, because the nearest bot is usually behind one.
- `tools/render_wall_moves.sh [run|runjump|chimney]` draws dm_atrium's wall routes from first person through `ArenaPlayer.present` at three frames a tick (`--fixed-fps 192`), saves a frame every two ticks and a sheet per route into `screenshots/wall_moves/`, logs every frame's eye and roll to a CSV, and prints the largest change of eye step, of vertical step and of roll per frame, and the roll's reversals. A step that changes only on the tick a velocity does (a slide's boost, a kick, a landing), and a roll with no reversals and no step over about 0.2 degrees a frame, is a smooth run.
- `tools/render_bots.sh [preset]` plays the offline client at a `bot_difficulty` (medium by default) and photographs one bot from over its shoulder every 0.4 s for 16 s (`screenshots/bots_<preset>_NN.png`), logging its state, its target, whether it can see that target and whether its trigger is down; `BOTS_DEBUG=1` adds every other player's distance, angle off the bot's view and line of sight. It is how a bot that looks like a machine is caught: the first run showed one pre-aiming the body of the player it had just killed. Its camera is placed in `RenderingServer.frame_pre_draw`, because the client writes its own camera every frame and anything earlier is overruled.
- `tools/render_feel.sh [bot|run|stairs|landing|strafe|slide]` draws what `headless_feel` measures at 144 frames against 64 ticks (`--fixed-fps 144`): a bot running across the view four metres off, every frame (`--stepped` draws it at its ticks, the control: 0 to 10.6 px a frame across the screen against an even 4.7), a run with the view model, every third frame, dm_box's stair at a run, and the camera's motion: a 5 m drop (every second frame from just before the landing), a strafe each way and a slide along the open lane at z -17, each logging the roll, dip and lens per frame. Writes `screenshots/feel/` with a sheet each, and prints each one's largest change of step. A tool that draws the view at the ticks' yaw zigzags the sway; it sets `view_now` per frame, as the client's sampler does.
- `tools/audio_probe.sh` asks whether the game makes a noise at all (it needs an audio device, so `xvfb-run`, never `--headless`); `tools/loudness_pilot.gd` is the loudness run's pilot ([footsteps](#footsteps-and-the-bed)).
- `~/stack/game-dev/tools/screenshot.sh game-arena out.png --wait 35 -- --offline` is the real offline client. Arena starts in warmup, so an early frame lies.

All need `xvfb-run`: under `--headless` every saved frame is empty, which looks like a screenshot.

## The frames around the loading cover

`tools/load_stall.tscn` (offline) and `client_bench.tscn -- --stall` (connected) record every wall-clock frame from the client's creation and split at the gate's `opened`: how long the cover is up, its worst frame, and the first seconds after it (fps, worst frame as a multiple of the median). Run under `xvfb-run -a godot --path . --rendering-driver opengl3 --resolution 480x270`; software GL is slow, so compare runs back to back and read ratios. `load_stall --budget N` exits 1 when the first seconds hold a frame over N times the median. The synthesised sound bank used to be baked in one 0.7 s frame (one frame of about 1.0 to 1.5 s in the cover, several seconds in a browser); it is now baked 6 ms a frame behind the gate's `sounds` hold, and `headless_presentation` checks the sliced bank equals the one-shot one. **In a real browser** (`tools/browser_stall.mjs`, RTX 2070 via `gpu.sh cdp`, 2026-10-22, `GPU_CDP_SERVE=8099` plus `ssh -R` for the server port; the client sets `window.arena_gate_open` under `cl_perf`): the first 2 s of play after the cover run 55-60 fps with a worst frame of 17-150 ms, before and after the bake slicing alike; shader compile and imports do not show after the drop (the cover's own material draw is 0.38 s). What is left is under the cover: the shell's `load()` of the pack's scripts is one 5.4 s frame (the worst frame in both runs, 6.6-6.7 s, so the bake slicing is invisible there), `add_child` 1.0 s, the map build 1.8 s. `--budget-ms N` fails when the first 2 s of play hold a frame over N. The script load is the shell's (dot-server-deploy, dot-cloud), not arena's. What is left in the cover's worst frame (about 0.45 s): `ArenaMap.to_scene` loading the surface texture sets synchronously (0.24 s).
